# Netlify + Render deployment

## Architecture and current status

The application is Next.js App Router with Next.js Route Handlers (not a separate Express backend). Render runs the complete Next.js service and PostgreSQL. Netlify runs the Next.js storefront using its maintained OpenNext adapter. On Netlify, `API_PROXY_ORIGIN` enables a server-side rewrite for `/api/*` to the Render service; the browser keeps same-origin URLs so NextAuth cookies remain first-party. The Netlify site does not need database credentials. The product detail page fetches its live catalog from Render when this proxy is configured; admin APIs continue to check the current database role.

Firebase is not currently used for authentication or storage. Authentication is NextAuth Credentials with the existing Prisma user records. Product images are remote CDN URLs, not Firebase Storage.

The Render Blueprint is configured for Free Web + Free Postgres because that was selected for a temporary preview. **This is not production-safe:** Render says Free Postgres expires 30 days after creation, then has a 14-day upgrade grace period before the database and its data are deleted. Free web services can sleep or be suspended. Before accepting real orders/payments, choose a persistent paid database plan in the Render Dashboard and confirm its cost manually.

The GitHub repository has been created and the project pushed. Render and Netlify services, provider configuration, and site-domain assignment still require dashboard/account access.

## Environment variables

| Variable | Render service | Netlify site | Notes |
| --- | --- | --- | --- |
| `DATABASE_URL` | Set by the Render Blueprint from the Render database’s internal connection string. | Not required. | Use internal URL for same-region Render service-to-database traffic. |
| `NEXTAUTH_URL` | Set to the Netlify production URL. | Set to the same Netlify production URL. | NextAuth endpoints are proxied through the Netlify origin. |
| `NEXTAUTH_SECRET` | Generated by Render. | Copy the exact same value from Render. | Required so the Netlify server can read the NextAuth JWT cookie. Never commit it. |
| `CORS_ORIGIN` | Set to the exact Netlify production origin, with no trailing slash. | Not required. | Render rejects requests carrying any other `Origin`. |
| `API_PROXY_ORIGIN` | Leave unset on Render. | Set to the Render service origin, e.g. `https://<actual-service>.onrender.com` (no path/trailing slash). | Must be present at Netlify build time for the `/api/*` rewrite. |
| `RAZORPAY_KEY_ID` | Razorpay **test** public ID. | Not required. | Keep Test Mode until a separate production-readiness review. |
| `RAZORPAY_KEY_SECRET` | Razorpay **test** secret. | Not required. | Server-only secret; do not place in `NEXT_PUBLIC_*`. |
| `RAZORPAY_WEBHOOK_SECRET` | Test webhook secret. | Not required. | Server-only secret. |
| `RAZORPAY_MODE` | `test`. | Not required. | The server rejects live keys when configured for test mode. |

`NEXT_PUBLIC_API_URL` is not used: the code already uses same-origin relative `/api/...` paths, and the Netlify server-side rewrite sends those to Render. No hardcoded absolute API URL needed replacing.

## Create Render resources

1. Sign in to Render and connect the public GitHub repository `my-fashionhub-ecommerce-website`.
2. Choose **New + → Blueprint**, select the repository and branch `main`, and approve the `render.yaml` Blueprint.
3. The Blueprint defines a Free Web Service named `fashion-hub-api` and a Free Postgres database named `fashion-hub-postgres`. It asks you to provide `NEXTAUTH_URL`, `CORS_ORIGIN`, and the three Razorpay test credentials. Use a temporary Netlify URL if the final site URL is not yet assigned; update it in Render after creating the Netlify site.
4. Wait for the database to become available and the service to deploy. Render uses the PostgreSQL **internal** connection string for `DATABASE_URL`.
5. In the database page, open **Connect** and copy the **External URL** only for the one-time local SQLite import below. Do not paste it into chat or commit it.
6. Copy the actual Render service origin from its dashboard. You will put it into the Netlify `API_PROXY_ORIGIN` setting.

The Blueprint build command runs `npm install`, `npx prisma migrate deploy`, then `npm run build`; start command is `npm start`; Render health check is `/api/health`.

## Preserve and import the existing SQLite data

The existing database is `prisma/dev.db`. It and all old SQLite migrations are preserved; `prisma/dev.db` is ignored by Git. Back it up before migration. The SQLite-to-PostgreSQL import refuses a PostgreSQL database containing application rows, preserves record IDs and timestamps, and verifies row counts transactionally.

The active Prisma schema now targets PostgreSQL. The local environment currently needs a PostgreSQL `DATABASE_URL` before database-backed local pages or API routes can run. Put the Render External URL (or another reachable PostgreSQL URL) in the ignored `.env.local` file; do not overwrite or commit local secrets. `SQLITE_SOURCE_URL` points the one-time importer at the archived SQLite database.

After Render’s initial deploy has created the empty PostgreSQL tables, stop local Next.js processes so SQLite is not being written. In PowerShell, set the external URL only in the current shell and run:

```powershell
$env:DATABASE_URL = "<Render External URL>"
$env:SQLITE_SOURCE_URL = "file:../dev.db"
npm run db:migrate:sqlite-to-postgres
Remove-Item Env:DATABASE_URL
Remove-Item Env:SQLITE_SOURCE_URL
```

The import generates the PostgreSQL client and archived SQLite client automatically. Verify the imported row counts and `/api/health` before using the app. Do not run the import a second time unless the target database is empty again.

For the Render service, continue using the **Internal URL** supplied by the Blueprint. Internal URLs are for same-region Render services; the External URL is for local tools/migration work.

## Create the Netlify site

1. Sign in to Netlify, choose **Add new site → Import an existing project**, authorize GitHub, and select `my-fashionhub-ecommerce-website` on branch `main`.
2. Use `npm run build` as the build command. Netlify’s current Next.js integration automatically detects the app and uses its maintained OpenNext adapter; no legacy pinned Next.js plugin is added.
3. Add these environment variables in **Site configuration → Environment variables**:
   - `API_PROXY_ORIGIN` = the actual Render service origin (HTTPS, no trailing `/`).
   - `NEXTAUTH_URL` = the Netlify production URL (for example `https://<site-name>.netlify.app`).
   - `NEXTAUTH_SECRET` = the exact value generated for the Render service.
4. Deploy. Then set `NEXTAUTH_URL` on Render and `CORS_ORIGIN` on Render to the final Netlify production origin. Redeploy both services after changing those settings.

Do not set `DATABASE_URL` on Netlify. Do not use Razorpay secrets on Netlify. Configure the custom domain in Netlify only if you own it and have DNS access; use the assigned Netlify URL otherwise.

## Seed, health, and redeploy

The Prisma seed command is configured as `node prisma/seed.js`. Run it against the Render database only if you intentionally want to upsert the bundled catalog:

```powershell
npx prisma db seed
```

Health checks:

- `https://<render-service>.onrender.com/api/health` should return `200` with `{"status":"ok","database":"connected"}` once database setup is complete.
- Open the Netlify site and verify the storefront, product detail page, registration/login, cart, wishlist, checkout, profile, and admin APIs.
- In browser developer tools, confirm `/api/*` requests are served through the Netlify origin and no browser CORS errors occur.
- Keep Razorpay in Test Mode and verify successful/failed test payments and webhook delivery before any live launch.

After both providers are connected to the GitHub repository, pushes to the configured production branch trigger builds/deployments. Check Render and Netlify deploy logs after each push; a successful build does not prove that authentication, database import, payment, or webhook configuration is correct.
